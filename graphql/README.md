# GraphQL Gateway

Combines all backend REST services into a single GraphQL API, implemented in Rust using [async-graphql](https://async-graphql.github.io/async-graphql/en/index.html) and [axum](https://github.com/tokio-rs/axum), built with [cargo-chef](https://github.com/LukeMathWalker/cargo-chef) (mirroring the `recipes-edit` Dockerfile/devcontainer setup).

Query/mutation fields are merged per domain module (`recipes`, `ratings`, `images`, `inspirations`, `image-inline`, `link-extract`, `traefik`) via `MergedObject`. Fields other domains contribute to `Recipe`/`Link`/`ExtractedLink` are added via `ComplexObject` - since Rust only allows one `impl ComplexObject` per type, those types are defined centrally (`src/recipe.rs`, `src/link.rs`) with field bodies delegating to the owning domain module.

Running `mise run merge-graphql-schemas` from the repository root builds the GraphQL application image from the current source and runs its `print-schema` command to distribute the SDL to consuming projects. It prepares missing Compose configuration, reuses available Docker build caches, and never uses a devcontainer. Schema generation needs no account map, auth provider, running server, or `REST_ENDPOINT`; build or generation failures leave existing schemas unchanged.

## Human identity and authorization

At runtime GraphQL requires the read-only JSON secret `/run/secrets/auth-accounts.json`, an object mapping verified email addresses to the fixed roles `member` or `owner`, for example `{"owner@example.com":"owner","family@example.com":"member"}`. Configure at least one owner; multiple owners are allowed. The local Compose service mounts the untracked `./.secrets/auth-accounts.json` file read-only at that path, and k3s deployments should mount a Secret read-only at the same path. Configure `AUTH_TRUSTED_ISSUER` explicitly; production uses `https://accounts.google.com`. Schema printing and event provisioning do not load either runtime auth setting.

Configured and incoming addresses are validated as conservative ASCII dot-atom local parts and DNS-style domains with at least two labels, then lowercased for lookup. No provider-specific aliases are merged. The issuer/subject pair is the stable account identity; email selects the current role and is not a permanent account or ratings identifier.

GraphQL accepts the sanitized `X-Auth-Request-User`, `X-Auth-Request-Issuer`, `X-Auth-Request-Email`, and optional `X-Auth-Request-Email-Verified` identity headers. The issuer must exactly match `AUTH_TRUSTED_ISSUER`; only the exact value `true` grants the role found in the startup-loaded map. Missing verification produces an authenticated identity without privileges. These headers are trusted only behind the auth-proxy sanitization and network boundary; this service alone does not prevent direct-access or spoofing.

Anonymous and unapproved identities can read public data and aggregate ratings; members additionally have comment and individual-rating capabilities; owners have those capabilities plus collection-wide recipe, import, image, and account-policy administration. Reusable capability guards provide structured `401 authentication-required` and `403 forbidden` errors. Applying guards to existing API fields and replacing caller-supplied rating logins are separate integration work.

The auth service owns its normal library-managed remembered/refreshing session lifetime; GraphQL imposes no separate absolute deadline. Role-map changes take effect only after GraphQL has restarted with the new file. During a multi-replica rollout, do not declare a revocation effective until every serving GraphQL replica has loaded the new map; stale replicas must be removed from service or restarted first. Existing sessions require no auth-proxy restart or user re-login for map changes. Successful session refresh may update the verified email and role lookup follows that new email. If refresh is rejected because email is unverified, the last validated identity may remain usable until its existing token expires; upstream claim revocation is not immediate.
